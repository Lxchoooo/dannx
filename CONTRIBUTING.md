# Contributing to DannX

Thanks for taking the time to contribute. DannX is a small, open-source Android
app, so clear reports and focused pull requests go a long way.

By participating, you agree to follow our [Code of Conduct](CODE_OF_CONDUCT.md).

## Before you start

- For bugs or feature ideas, open an issue first.
- For security problems, **do not** open a public issue: follow
  [SECURITY.md](SECURITY.md).
- Keep pull requests small and focused. One topic per PR is easier to review and
  faster to validate in CI.

## Requirements

- JDK 17.
- Android SDK 37. The app targets SDK 36 and supports Android 10 (API 29) and
  newer.
- Use the committed Gradle wrapper (`./gradlew`), not a local Gradle install.

The app works with its built-in demo feed. To point it at a Supabase project,
create `local.properties` (not committed) or export the variables:

```properties
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_ANON_KEY=your-anon-key
```

`SUPABASE_ANON_KEY` is public by design. Never put a service-role key in the app
or in the repository.

## Build and test

```bash
./gradlew assembleDebug        # debug APK
./gradlew lintDebug            # lint report
./gradlew testDebugUnitTest    # JVM unit tests
./gradlew assembleRelease      # signed release APK (needs the keystore)
```

`assembleDebug` uses the release keystore when `ANDROID_KEYSTORE_PATH` is set;
CI does this so debug artifacts install over the published release. Without the
keystore, Gradle falls back to the standard debug key.

## Project layout

```
app/src/main/java/com/dannx/walls/
├── data/      # API client, cache, preferences, demo feed, retry policy
├── ui/        # screens, components, theme, window size classes
└── util/      # wallpaper files, download/apply helpers, geometry
.github/       # CI workflows and repository automation
docs/          # screenshots, designs and database migrations
```

## Code style

- Kotlin with 4-space indentation, trailing commas and no wildcard imports.
  Follow the existing `.editorconfig`.
- Keep composables stateless where possible: pass state and callbacks down.
- All user-facing text belongs in `app/src/main/res/values/strings.xml` and
  `app/src/main/res/values-en/strings.xml`. Use `stringResource` in Compose and
  `StringResolver` outside it. Do not hardcode UI strings.
- Mark UI state and models as immutable when they are used by Compose.
- Add JVM tests for pure logic. `EditorBlurTest` is a good example.
- Avoid new dependencies unless they are necessary; explain the reason in the PR.

## Tests

- Unit tests live in `app/src/test/` and run on the JVM.
- Add a regression test for every bug fix that can be tested without a device.
- Instrumented tests and emulator-only changes need a note in the PR because CI
  does not run them.

## Commits and pull requests

- Branch from `main`; do not commit directly to it.
- Use clear commit messages. Spanish or English are both fine.
- Fill in the pull request template: what changed, why, and how you tested it.
- UI changes should include a screenshot or a short recording.
- `checks` (lint + unit tests) and `debug` must be green before merging.
- Never commit secrets, keystores, tokens, `local.properties`, or build outputs.

## Translations

- Add every new key to both `values/strings.xml` and `values-en/strings.xml`.
- Use `<plurals>` when the text depends on a number.
- Keep demo data and the debug FPS overlay untranslated.

## Releases

The maintainer publishes releases:

- A tag `vX.Y.Z` creates a signed versioned release.
- Every merge to `main` refreshes the rolling `DannX · última versión` release.
- Release notes and the APK checksum are generated by CI, together with a build
  provenance attestation.
